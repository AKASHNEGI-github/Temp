# JWT (JSON Web Token) – Complete Interview Guide

## 1. What is JWT?

JWT stands for **JSON Web Token**.

JWT is an open standard (RFC 7519) used to securely transmit information between two parties as a JSON object. It is commonly used for authentication and authorization in REST APIs and distributed applications.

In simple terms, JWT is a token generated by the server after successful login. The client sends this token with subsequent requests, and the server validates it to identify the user and determine their permissions.

### Why do we use JWT?

Consider an e-commerce application:

1. A user logs in with a username and password.
2. The backend validates the credentials.
3. The backend generates a JWT.
4. The JWT is sent to the client.
5. The client stores the token.
6. For every protected API request, the client sends the JWT.
7. The backend validates the JWT and allows or denies access.

**Advantages of JWT:**

- Enables stateless authentication.
- No need to maintain a server-side session for every user.
- Useful for REST APIs.
- Works well with mobile applications.
- Supports distributed systems and microservices.
- Can carry user information and permissions as claims.

## 2. JWT Structure

A JWT consists of three parts:

**Header.Payload.Signature**

### A. Header

The header contains information about the token type and signing algorithm.

Example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- `alg`: Algorithm used to sign the token.
- `typ`: Token type, usually JWT.

### B. Payload

The payload contains claims (information about the user and token).

Example:

```json
{
  "sub": "101",
  "name": "John",
  "role": "ADMIN",
  "iat": 1795500000,
  "exp": 1795503600
}
```

Important claims:

| Claim | Meaning |
|---|---|
| `sub` | Subject (usually user ID) |
| `iss` | Issuer (who generated the token) |
| `aud` | Audience (intended recipient) |
| `iat` | Issued at |
| `exp` | Expiration time |
| `nbf` | Not before |
| `jti` | Unique token ID |

**Important:** JWT payload is Base64URL encoded, not encrypted by default. Anyone possessing the token can decode and read its payload. Never store passwords or sensitive information in it.

### C. Signature

The signature ensures that the token has not been modified after it was issued.

For example, using HS256:

```text
Signature =
HMACSHA256(
  Base64Url(Header) + "." +
  Base64Url(Payload),
  SecretKey
)
```

The server uses the appropriate verification key to validate the signature.

If someone modifies the payload, signature verification fails.

## 3. How Does JWT Authentication Work?

1. **Login request:** Client sends username and password to the backend.
2. **Credential validation:** Backend checks the credentials against the database.
3. **Token generation:** If credentials are valid, the backend generates a JWT using a signing key.
4. **Token response:** Backend sends the JWT to the client.
5. **Token storage:** Client stores the token securely.
6. **API request:** Client sends the token with every protected API request.

Example:

```http
GET /api/user/profile
Authorization: Bearer <JWT_TOKEN>
```

7. **Token validation:** Backend verifies:
   - Token signature.
   - Token expiration.
   - Issuer and audience, when applicable.
   - Other required claims.

8. **Access granted:** If the token is valid and the user has the required permissions, the backend processes the request.

If the token is invalid or expired, the server rejects the request.

---

## 4. What Are the Different Types of JWT Claims?

Claims are statements about the user or token.

There are three categories:

| Type | Description | Examples |
|---|---|---|
| Registered claims | Standard predefined claims | `iss`, `sub`, `exp`, `iat` |
| Public claims | Custom claims with names designed to avoid collisions | `role`, `department` |
| Private claims | Custom claims agreed upon between communicating parties | `userId`, `employeeId` |

Example:

```json
{
  "sub": "101",
  "role": "ADMIN",
  "department": "IT",
  "exp": 1795503600
}
```

## 5. What Are the Different JWT Signing Algorithms?

JWT supports different algorithms to generate and verify signatures.

| Algorithm | Description |
|---|---|
| HS256 | HMAC using SHA-256 (symmetric key) |
| HS384 | HMAC using SHA-384 (symmetric key) |
| HS512 | HMAC using SHA-512 (symmetric key) |
| RS256 | RSA using SHA-256 (asymmetric keys) |
| RS384 | RSA using SHA-384 |
| RS512 | RSA using SHA-512 |
| ES256 | ECDSA using SHA-256 |

### HS256 vs RS256

| HS256 | RS256 |
|---|---|
| Symmetric algorithm | Asymmetric algorithm |
| Uses one shared secret key | Uses private and public keys |
| Same secret signs and verifies | Private key signs; public key verifies |
| Suitable when trusted parties share a secret | Useful in distributed systems and microservices |

**Example:**

- HS256: Authentication server and API server share the same secret.
- RS256: Authentication server signs the token with a private key, while multiple API services verify it using the public key.

## 6. What Is the Difference Between Access Token and Refresh Token?

### Access Token

- Used to access protected APIs.
- Usually has a short expiration time.
- Sent with API requests.
- Contains claims such as user ID and permissions.

### Refresh Token

- Used to obtain a new access token when the existing access token expires.
- Usually has a longer lifetime.
- Should be stored securely.
- Should be revocable and preferably rotated when used.

| Comparison | Access Token | Refresh Token |
|---|---|---|
| Purpose | Access protected resources | Generate new access tokens |
| Expiration | Short-lived | Longer-lived |
| Sent to | Resource/API server | Authentication server |
| Usage | Every protected API request | When renewing access |
| Security | Must be protected | Requires especially careful protection |

### Refresh Token Flow

1. User logs in.
2. Server generates an access token and refresh token.
3. Client uses the access token to call APIs.
4. Access token expires.
5. Client sends the refresh token to the refresh endpoint.
6. Server validates the refresh token.
7. Server issues a new access token, and potentially a rotated refresh token.
8. Client continues accessing APIs.

**Interview point:** A refresh token should not be sent with every API request. It should only be used with the appropriate token-renewal endpoint.

---

## 7. What Happens When a JWT Expires?

When a JWT expires:

- The backend rejects the expired access token.
- The client can use a valid refresh token to obtain a new access token.
- If the refresh token is also expired or revoked, the user needs to authenticate again.

Example:

```json
{
  "sub": "101",
  "role": "ADMIN",
  "exp": 1795503600
}
```

The `exp` claim represents the token expiration time in Unix seconds.

## 8. What Are the Advantages and Disadvantages of JWT?

### Advantages

1. Stateless authentication is possible.
2. No session database lookup is required for self-contained tokens.
3. Easy integration with REST APIs.
4. Suitable for microservices architecture.
5. Supports claims-based authorization.
6. Can be used across different platforms such as web and mobile applications.

### Disadvantages

1. Difficult to revoke immediately without additional infrastructure.
2. If stolen, a valid token can be misused until it expires or is revoked.
3. Token size can increase when too many claims are included.
4. Requires secure storage on the client.
5. Changes to user roles may not immediately reflect in an already-issued token.
6. Token expiration and refresh management add complexity.

---

## 9. Is JWT Secure? How Do You Protect JWT?

JWT can be secure when implemented correctly.

Important security practices:

- Always use HTTPS.
- Keep access tokens short-lived.
- Never store passwords or sensitive information in JWT payloads.
- Validate the signature.
- Validate `exp`, `iss`, and `aud` as applicable.
- Use strong signing keys.
- Never accept an unexpected signing algorithm.
- Protect tokens against XSS and CSRF depending on how they are stored and transmitted.
- Rotate refresh tokens and detect refresh-token reuse.
- Implement token revocation when necessary.

**Important interview point:**

JWT is not encrypted by default. It is generally signed, which protects integrity, not confidentiality.

## 10. JWT vs Session-Based Authentication

| Comparison | Session-based | JWT-based |
|---|---|---|
| Authentication type | Stateful | Usually stateless |
| Where data is stored | Server | Claims inside token |
| Client stores | Session ID | JWT |
| Server validation | Session store lookup | Signature and claims validation |
| Scalability | Requires shared session storage in distributed environments | Easier to scale without shared session storage |
| Logout | Destroy the session | Revoke token or wait for expiry |
| Server memory | Stores session information | No per-user session storage required for self-contained tokens |
| Common usage | Traditional web applications | REST APIs and distributed systems |

## 11. What Is the Difference Between Authentication and Authorization?

Interviewers often ask this along with JWT.

| Authentication | Authorization |
|---|---|
| Verifies who the user is | Determines what the user can access |
| Happens first | Happens after authentication |
| Checks credentials or token identity | Checks roles and permissions |
| Example: User login | Example: Admin-only API access |

**Example:**

- Authentication: Is this user John?
- Authorization: Is John allowed to delete a product?

JWT can support both by carrying identity and permission-related claims, but the backend must still enforce authorization rules.
